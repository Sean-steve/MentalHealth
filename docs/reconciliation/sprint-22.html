Sprint 22 reconciliation

PARTIAL — PRODUCTION CERTIFICATION PENDING

MindOS Sprint 22 is no longer only a domain prototype. Care Plans, Clinical Tasks and Professional Messaging now have runtime/API wiring, PostgreSQL repositories, migration coverage, maintenance orchestration and hardened safety/authorization boundaries. It is intentionally not marked complete until the full dependency-backed Sprint 1–22 regression can run.

Implemented

  • Care Plans: versioned plan lifecycle, governed review cadence, user-acknowledgement gate, goals, interventions, assignments, reviews and progress projection.
  • Clinical Tasks: dependency graph/cycle prevention, relationship-scoped assignment, owner-domain completion, evidence, overdue/readiness reconciliation, bounded recurrence, policy-configured recurrence, reminder deduplication and persistent reminder receipts.
  • Professional Messaging: care-relationship-scoped threads, participants, protected content references, idempotent send, delivery/read states, notification integration, same-thread reply validation, relationship closure, privacy-preserving Safety forwarding and deny-by-default attachment governance.
  • PostgreSQL: Care Plan, Clinical Task and Professional Messaging repositories are wired for production mode through mindos/sprint22/runtime.ts; migration 020_canonical_care_plans_tasks_messaging.sql covers the Sprint-22 persistence model.
  • API: Sprint-22 routers are mounted under /api/v1 from the main server. External APIs reject SYSTEM task creation, owner-domain completion forgery, client-defined messaging response expectations and invalid enum/state values.

Durability & concurrency hardening

  • Core Care Plan, Clinical Task and Professional Messaging mutations use application-owned UnitOfWork transactions with canonical transactional-outbox events.
  • Care Goal review now persists the goal mutation + review record atomically and registers care.goal_updated through the outbox.
  • Content and Assessment assignments now persist atomically with care.assignment_created.
  • Clinical Task persistence has optimistic state checks, idempotency keys and authoritative completion evidence.
  • Professional Messaging has optimistic delivery/thread updates and idempotent message creation.
  • Care Plan review execution now persists an atomic reviewer/outcome intent before plan mutation, uses a preallocated version ID for MODIFY, resumes after partial failure without duplicating versions, blocks outcome switching, and persists care.plan_review_completed through the transactional outbox.

Authorization & clinical-integrity hardening

  • Care Goal creation independently revalidates the plan/relationship at the service boundary; users may create only their own USER_SELECTED goals.
  • Professional Care Goal and Care Intervention creation requires relationship-scoped Care Plan write access and the current editable plan version.
  • Task start/completion revalidates assignment, relationship state and care-team membership; relationship termination races fail closed.
  • Care Plan reviews reject stale plan versions and cross-plan goal reviews.
  • Active/superseded Care Plan versions cannot be silently mutated in place.
  • No guessed 30-day clinical review cadence remains.

Safety & communication boundaries

  • Care-message metadata never needs raw message content; Safety integration works through a protected-content classifier port and forwards qualifying candidates into the authoritative CrisisResponseOrchestrator.
  • The runtime reports messaging Safety as EXPLICIT_SCANNER_REQUIRED unless a governed protected-content classifier is provided.
  • MindOS does not reuse the AI Companion keyword pre-check as Professional Messaging clinical monitoring without governance approval.
  • Attachments fail closed until a governed file/media policy verifies malware scan, MIME/size and data-classification requirements.
  • Messaging never claims real-time clinician/emergency monitoring.

  • Full foundation import: the GitHub repository still does not contain the complete Sprint 1–21 foundation. The original archive has been recovered and audited, but the current connector/runtime boundary cannot bulk-stream those local bytes into GitHub.
  • Executable regression: after the foundation is present in GitHub, run dependency-backed typecheck, Sprint 1–22 tests, PostgreSQL migration validation, integration/E2E, security/privacy, event-contract and production build checks.
  • Messaging Safety classifier: configure an explicitly governed Professional Messaging protected-content classifier. The existing AI Companion raw-text pre-check is purpose-specific and is not being silently repurposed.
  • Attachment/media adapter: connect the deny-by-default attachment policy to an approved media scanning/storage service before attachments can be enabled.

Current decision: Sprint 22 is functionally and architecturally advanced, with major production durability/security gaps closed. Status remains PARTIAL until the full foundation can be regression-tested and the governed messaging Safety/media adapters are configured.
