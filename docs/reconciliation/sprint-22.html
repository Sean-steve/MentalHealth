Care Plans & collaborative care

  • Versioned Care Plan lifecycle with immutable active versions and new-version semantics for material changes.
  • Relationship-scoped goals and interventions with provenance, current-version guards and user USER_SELECTED constraints.
  • Content and Assessment assignments reuse governed owning domains and persist atomically with outbox events.
  • Care Plan reviews use an atomic reviewer/outcome claim, retry-safe MODIFY saga, preallocated version IDs, compare-and-set completion and exactly-one logical completion event.
  • Stale review, cross-plan goal, user-acknowledgement and terminal-plan resurrection protections are covered by acceptance tests.

Clinical Tasks

  • Relationship-scoped task model with task type, assignee, priority, authoritative state machine and evidence.
  • Dependency graph, cycle prevention, readiness, overdue reconciliation and owner-domain completion anti-spoofing.
  • Bounded recurrence creates only the next occurrence from an explicitly configured versioned policy; no hidden cadence is guessed.
  • Policy-driven reminders use persistent receipts to prevent duplicate notifications.
  • Relationship termination and care-team changes are revalidated at action time and fail closed.

Professional Messaging

  • Threads and participants are tied to active care relationships, purpose and relationship-scoped authorization.
  • Raw care-message content is accepted only through the protected-content endpoint, encrypted immediately, and thereafter referenced by opaque content ID.
  • Message metadata is idempotent and protected by transactional outbox/optimistic concurrency.
  • Reply references are same-thread validated; relationship termination blocks new messages immediately before asynchronous reconciliation.
  • Notification payloads remain privacy-minimized and messaging does not claim real-time clinician or emergency monitoring.

Safety integration

  • Default runtime uses the governed deterministic acute-distress rules already present in MindOS rather than an invented messaging heuristic.
  • Protected content is decrypted only inside the controlled Safety-scanner boundary; ordinary message metadata never carries raw text.
  • User messages preserve USER_SELF_REPORT / USER_REPORTED provenance; professional messages preserve professional provenance.
  • The messaging scanner emits only candidate SafetySignals. Canonical RiskState, SafetyAction and escalation remain owned by the Safety Kernel/CrisisResponseOrchestrator.
  • Missing protected content fails closed instead of allowing an unevaluated message to masquerade as monitored.

Secure attachments

  • Attachment linking is governed by explicit deployment policy with no hard-coded product size/MIME defaults.
  • Only CLEAN-scanned attachments within configured MIME, size and data-classification policy are accepted.
  • Public HTTP(S), data and browser blob references are rejected; messaging stores only protected evidence references.
  • Deny-by-default remains the fallback when a deployment has not supplied an attachment policy.

Persistence, API & runtime

  • PostgreSQL repositories are implemented for Care Plans, Clinical Tasks and Professional Messaging.
  • Migration 020_canonical_care_plans_tasks_messaging.sql includes plans, versions, goals, interventions, reviews, assignments, tasks, dependencies/evidence/reminder receipts, messaging threads/participants/messages, encrypted protected content and attachments.
  • Sprint-22 routers are mounted under /api/v1, including protected message-content storage and metadata send endpoints.
  • Production runtime configures PostgreSQL, notifications, deterministic messaging Safety classification, attachment policy and recurrence/reminder policy boundaries.
